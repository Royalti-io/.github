# Contributing

Thanks for looking. What's useful here depends on which repo you're in.

## The repos

- **[`royalti-api-skill`](https://github.com/Royalti-io/royalti-api-skill)** — corrections are
  especially welcome. If the skill describes an endpoint, parameter or response shape that
  doesn't match what the API actually does, that's a bug worth reporting, and a PR fixing it
  is worth more. Say which endpoint and what you observed.
- **[`post-build-cliff`](https://github.com/Royalti-io/post-build-cliff)** — corrections,
  broken links, and lessons that no longer match the tools they describe.
- **[`payloadcms-social-media-plugin`](https://github.com/Royalti-io/payloadcms-social-media-plugin)**
  — bug reports and PRs against the plugin surface.

The Royalti platform itself is closed source. Bugs in the hosted product are better sent to
support than filed here — we'll see them faster.

## Before you open a PR

- **Open an issue first** for anything beyond a typo or an obvious fix. It's a cheap way to
  find out whether the change fits before you write it.
- **One concern per PR.** Two unrelated fixes are two PRs.
- **Say what you verified.** "Checked against a live API response" is worth more than
  "should work".

## Accuracy bar

Several of these repos document how the music industry actually works — royalty accounting,
DDEX delivery, rights registration. People make real decisions from that material.

So: claims about a spec, a standard, or a third-party system need a source. If you're
correcting something, say what you checked it against. "I think it's X" is a fine issue and a
poor PR.
